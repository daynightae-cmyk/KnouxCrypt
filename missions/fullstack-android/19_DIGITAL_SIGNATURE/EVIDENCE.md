## What works

- `DigitalSignatureService` (`:core:security`): detached signatures over the SHA-256 digest of the
  content with SHA-256/ECDSA-P-256 or SHA-256/RSA-2048, both selected by what the device's
  Keystore supports. Verification distinguishes four verdicts — valid, content changed (digest
  mismatch), invalid signature, malformed — and refuses any other algorithm.
- `SigningService` (`:core:data`) reports where the key actually lives:
  - `KEYSTORE`: an asymmetric key generated by the Android Keystore (the private half never
    leaves the platform), or
  - `VAULT_SOFTWARE`: a software EC key pair whose private half is stored as an **encrypted vault
    record**, i.e. protected by the Keystore-rooted data-key hierarchy but explicitly *not*
    hardware-backed. The screen says which one is in use.
  This fallback exists because of a real device finding: the itel S686LN's
  AndroidKeyStore provider answers "no such algorithm: EC for provider AndroidKeyStore" and the
  same for RSA — it only implements AES. Without the fallback, TASK 19 would have been dead code on
  exactly the handset we can test.
- `DigitalSignatureScreen` (route `signature`, catalog `SIGNATURE` implemented, unlock-required):
  sign text and store the record, list stored signatures, verify a stored signature against pasted
  content, verify an external signature from a pasted public key and signature, copy the public key
  or the signature under the managed clipboard lease, and read the verdict with its reason
  ("content changed" vs "invalid signature" vs "malformed"). A stored record keeps the signature,
  the digest, the public key and the algorithm — never the signed document.
- The honest limits are on screen: a valid signature proves possession of the matching private key
  and nothing more; it is not an identity claim and not an attestation.
